# 🎨 素材工作流：GPT 做設計 ＋ Claude 寫程式 ＋ Gemini 配音

> 初版 2026-08-18｜**分工改版 2026-08-20**
> 目標：**新增一款遊戲時，從企劃到素材進遊戲全自動**，你只要在幾個關鍵路口說「好」或「這個改一下」。

---

## 一、分工（2026-08-20 改版）

```
你          ：說「我要做一款 XXX 遊戲」→ 看企劃書點頭 → 看設定圖點頭 → 看 contact sheet 驗收 → 玩
ChatGPT     ：遊戲企劃 → 畫面/場景設計 → 設定圖 → 素材清單 → 生圖
Claude（我）：寫程式 → 驅動瀏覽器 → 去背/裁切/縮放 → 驗收 → 接線 → 改版號
Gemini      ：旁白 TTS
```

**跟舊版差在哪：** 舊版 ChatGPT「只做一件事——照 prompt 生圖」，企劃與素材規格是我寫的。
改版後**設計工作整段交給 GPT**，我只負責把它的產出變成能跑的程式。

**沒變的界線：GPT 不做去背、不做裁切、不做命名、不寫程式。**
它的 Python 沙盒確實能去背裁切，但那是每次都要重講一遍、結果不可重現的做法。
這些是純機械運算，放本機 PowerShell 才能版本控制、才能改一次參數整批重跑，而且**不燒生圖額度**。

> **背景音改由 Claude 用 Web Audio 合成**，不再列進 GPT 的職責——它產不出音檔，
> 舊版分工表寫了但四個階段裡從來沒有音訊產物，是個空頭支票。

## 二、ChatGPT Project 怎麼用（改版的核心）

一款遊戲 = 一個 ChatGPT Project。Project 有兩個地方可以放東西，**分配原則是實測出來的**：

| | 放什麼 | 為什麼 |
|---|---|---|
| **Instructions** | 每張圖都必須遵守的**鐵則**（單一主體／無文字／四邊留白／背景色規則／一致性／只畫一個姿勢） | 永遠在 context 裡，不靠檢索。但要**短**——長指令會稀釋服從度 |
| **Sources** | 企劃約束、技術限制、規範細節與理由、**素材清單**、**設定圖** | 是 RAG，**要用才撈**，不佔每則訊息的成本 |

> **實測依據**（詳見 [`snippets/chatgpt-dom.md`](snippets/chatgpt-dom.md) AE）：
> 在新對話裡問「這個專案的素材規劃裡，第一批包含哪幾個 ID？」，**完全沒提檔名**，
> 它正確答出 `CH101/CH201/CH301/EV001/EV002/EV101/TP001`（與 `assets.json` 完全吻合），還自己標了引用來源。
> 所以檢索是自動的。**但那是一則「明顯在問資料」的訊息**——生圖訊息長得不一樣，不保證觸發檢索。
> 所以鐵則不能只放 Sources。

### Sources 裡放什麼

| 檔名 | 內容 | 誰維護 |
|---|---|---|
| `00-專案總則與分工.md` | 專案是什麼、三方分工、階段 0~4 的交付物、文件索引 | 通用，每個 Project 推同一份 |
| `01-玩家與企劃約束.md` | 體感訊號白名單／黑名單、4 歲玩家的硬限制 | 通用 |
| `02-場景與技術約束.md` | 程式端做得到什麼、堆疊建築禁令、分層構圖 | 通用 |
| `03-美術規範與已知失敗模式.md` | 每張圖的規範、去背友善規則、fail 清單 | 通用 |
| `04-素材命名與交付格式.md` | ID 前綴、JSON schema、各種交付骨架 | 通用 |
| `05-設定圖流程（角色與場景）.md` | REF 設定圖怎麼生、怎麼引用 | 通用 |
| `<代號>-企劃書.md` | GPT 產出，我存回 repo 再推回來 | 每款一份 |
| `<代號>-場景設計.md` | 同上 | 每款一份 |
| `<代號>-素材清單.md` | 由 `tools/asset-list-source.ps1` 從 `assets.json` 產生 | 每款一份 |
| `REF001.png` `REF101.png` … | 角色／場景設定圖，檔名就是引用時要打的字 | 每款數張 |

通用六份的原始檔在 [`project-resources/`](project-resources/)，**repo 是唯一真相**。

### 雙向管線（2026-08-20 全部實測通過）

```
repo ──file_upload──► Project Sources
     檔名原封保留，.md 與 .png 都吃，單次總量 < 10 MB
     （要先複製到本 session 的 scratchpad；專案原路徑會被工具拒絕）

Project 對話 ──blob <a download>──► Downloads ──shell──► repo
     圖片與長文字都適用，無截斷
     （分段讀 innerText 不行：javascript_tool 回傳約 1000 字元就截斷）
```

> ⚠️ **Source 不能改名、不能編輯，只有 `Download` / `Delete`。**
> 所以規格一律在 repo 改，改完整份重推；`Add from library` 也因此不能用來放設定圖
> （會拿到圖庫自動取的英文標題，改不掉，prompt 就指不準）。
> `Delete` 不可逆，自動化不要自己按。

## 三、設定圖機制：角色與場景都適用（改版的核心之二）

一款遊戲有多個角色、一個角色有多個姿勢、或一個場景要拆層／出多個時段時，
**先生一張設定圖，存進 Sources，之後所有相關的圖都引用它**。

```
① 生設定圖：角色＝多視角＋多表情放一張；場景＝該場景的全景基準（分層、色調、光線方向）
② 下載成 REF001.png（角色）/ REF101.png（場景）—— 檔名就是之後要引用的字串
③ file_upload 進 Project Sources
④ 之後每張：「完全沿用 REF001.png 裡那個角色，配色與配件一模一樣，不要改造型」＋這張要的姿勢
```

> **前綴一定要用 `REF`，不能用 `CH`／`BG`。** `CH001` 在遊戲7 已經是主角的站立影格，會撞號。

### 實測結果（2026-08-20，遊戲7 的小師傅）

先用**不花生圖額度**的文字探針確認模型真的看得到：

> 先不要生圖。請打開 Sources 裡的那張角色圖，描述你**實際看到**的外觀……看不到就老實說。

它答出：黃色安全帽上有紅色圓徽與「廟」字、兩側青綠雲紋、白色短袖 T、藍色吊帶牛仔褲、紅領巾、
黃橘工作靴配紅鞋帶與深咖啡鞋頭、約 3 頭身、腰間工具帶與鐵鎚、背後斜插捲筒圖紙。
**細節密度不可能是從檔名猜出來的。**

接著在同一個新對話請它生「跳起來歡呼」：

| 項目 | 結果 |
|---|---|
| 安全帽（黃底＋紅圓徽＋「廟」字＋綠雲紋）、紅領巾、白 T、藍吊帶褲、胸前金色圖案 | ✅ 全對 |
| 黃橘工作靴＋紅鞋帶＋深色鞋頭、黃黑手套、工具帶＋鐵鎚、背後捲筒 | ✅ 全對 |
| 三頭身比例、指定的跳躍歡呼姿勢 | ✅ 對 |
| **「面向右邊」** | ❌ 沒服從，畫成正面偏左 |
| **「背景全透明」** | ❌ 沒服從，白底 |

### 所以要誠實地說它解決什麼

> **設定圖解決「設計一致性」——同一個角色、同樣的配色配件比例。**
> **它不解決「指令服從度」，也不解決「幾何一致性」。**

方向、背景、構圖照舊會漂，靠本機後處理與人眼收尾。
**不要因為加了設定圖就以為可以省掉驗收那一步。**

### 一個一定要寫進 prompt 的防呆

設定圖本身是「多視角設定表」，模型很可能連版面一起抄，交出一張設定表而不是單一姿勢。
所以每張 prompt 都要明寫：**只畫一個姿勢、單一主體、不要畫成多格設定表、不要有分格線。**

## 四、⚠️ 一條要修的帳：`build.ps1` 並沒有做幾何正規化

**這是 2026-08-20 查證出來的，先前的文件（包括這份 README 的舊版）都寫錯了。**

舊版寫著「讓素材真的能用的是本機的 `build.ps1` 幾何正規化（統一尺度 → 統一水平中心 → 統一底線），
這是整套工作流最有價值的一塊」。**實際去讀程式碼，這段功能不存在：**

- `tools/build.ps1` 全檔**沒有**「組／正規化／baseline／基準線」任何一個字。
  它只讀 `$a.id` 與 `$a.輸出.{knee, 裁切, 水平翻轉, 格式, webp品質, 去背, 純色容差, 邊緣淡出, w, h}`。
  做的事是：三路分流去背 → 邊緣羽化 → 依內容裁切或整張縮放 → 需要時水平翻轉 → 存 WebP。
- `assets.json` 的 **`組` 欄位從頭到尾沒有被任何腳本讀過**。`qa.ps1` 也不讀它——
  它是用寫死的 ID regex 分組（`^RUN\d+$` / `^CHAR0\d{2}$` / `^CHAR1\d{2}$` / `^CHAR2\d{2}$`），
  **只認得遊戲8 的舊 ID**；遊戲7 與任何新遊戲的 ID 全部落到空組，同組檢查根本不會執行。

**幾何實際上是誰補的：** 是我在遊戲程式端逐張吸收的。
遊戲7 的 `index-新美術.html` 把每張圖的實際長寬比寫死成 `AR` / `KID_FRAMES` / `VEH` 表，
再逐張給一個世界高度（小師傅四張是 1.75 / 1.25 / 2.15 / 2.15，挑法是讓「角色本人」看起來一樣大，
不是讓圖一樣高），最後用 `position.y = h / 2` 把腳底貼齊。

**「不要寫幾何規格」這條指令依然正確，但理由要改：**
不是「本機會修好」，而是**服從率接近 0**（見下一節的實測數字）。

### 這條帳留下的 TODO

| # | 待辦 | 影響 |
|---|---|---|
| 1 | `qa.ps1` 的分組改成讀 `assets.json` 的 `組` 欄位，而不是寫死的 ID regex | 現在新遊戲完全量不到同組一致性 |
| 2 | `qa.ps1` 的 `PALETTE_DRIFT` 招牌色寫死成遊戲8 松鼠配色（橘/米/藍/深棕），要改成每款可設定 | 換一款遊戲會誤判 |
| 3 | 要不要真的在 `build.ps1` 實作同組正規化 | **會改變既有輸出**，而遊戲端已針對現況調好每張的世界高度，貿然加上去會弄壞已上線的遊戲7/8。建議做成**每組 opt-in**，新遊戲才用 |

## 五、這條工作流真正的瓶頸

> **瓶頸不在按鍵次數，在模型畫不準。**

| 量到的事 | 數字 |
|---|---|
| 同角色不同影格「高度佔畫布比例」落差 | **19.8 個百分點**（規格希望 ±3pp） |
| 水平中心飄移 | **8.5pp**（規格希望 ±2pp） |
| 底部基準線落差 | **16.6%** |

而這是在「有附參考圖、同一個 Project、指令寫得很細」的條件下量到的。
設定圖機制改善的是**造型一致性**，這組**幾何**數字它救不了。

所以自動化省下的是「複製貼上與點按」的工，**它不會讓素材變好**。
最後的「好不好看」交給人眼看一張 contact sheet，一次批准整批。

## 六、已實測的機制

### ✅ 可行

| 機制 | 做法 | 實測結果 |
|---|---|---|
| 進專案開新對話 | `navigate` 到 `chatgpt.com/g/g-p-<id>/project`，直接在輸入框送出 | 自動在專案底下開新對話 |
| 灌入長 prompt | `document.execCommand('insertText', …)` 對 `#prompt-textarea` | 完整灌入，不會誤觸送出 |
| 送出 | `[data-testid="send-button"].click()` | — |
| 判斷還在生成 | `[data-testid="stop-button"]` 存不存在 | 最可靠的訊號 |
| 找到生成的圖 | 全域 `img[alt^="Generated image"]`，取最後一張 | — |
| 拿到全解析度原圖 | 對話裡的 `<img>` 就是原圖，不必點開燈箱 | `naturalWidth=1536` |
| 存成我指定的檔名 | blob → `<a download="REF001.png">` → `Downloads\` | 檔名完全由我控制 |
| **取回長文字產出** | 同一招 blob 下載 | 10,399 字元完整無損 |
| **推檔案進 Sources** | `file_upload` ＋ `find` 拿 dialog 裡的 file input ref | **檔名原封保留**，`.md`／`.png` 都吃 |
| **Sources 圖片被後續對話看到** | 在 prompt 裡寫檔名 | 見第三節 |
| **Sources 文件被自動檢索** | 不用指名 | 見第二節 |
| 壓成 WebP | `ffmpeg -c:v libwebp -quality 80` | **省 88~92%**，alpha PSNR = `inf` |

### 🔁 實跑後才發現的

| 以為 | 實際 |
|---|---|
| 用 `ref` 或座標點按鈕 | **會靜默失敗**。一律用 JS `.click()` |
| `.click()` 就能切 Sources 分頁 | **不行**，`button[role=tab]` 要先 `pointerdown` 再 `click()` |
| 生成的圖在 assistant 訊息容器裡 | **不在**。要全域找 `img[alt^="Generated image"]` |
| 抓到 img 元素就能讀圖 | 圖是 lazy-load，要先 `scrollIntoView()` + `loading='eager'` |
| 數「有幾張圖」判斷進度 | 對話虛擬捲動會把圖移出 DOM。要看「最後一張的 alt」 |
| 停止鍵消失 = 圖好了 | 還要 `naturalWidth >= 512` |
| 送出後輸入框會清空 | **不會**，每次送出後要強制清 |
| `javascript_tool` 可以在頁面裡等到好 | 有 **45 秒硬逾時**，且回傳約 **1000 字元**就截斷 |
| 遊戲在背景分頁也會跑 | **不會**，`requestAnimationFrame` 被凍住，實機驗證要讓分頁在前景（或靠截圖逼出影格） |

### ❌ 不可行

| 想做的事 | 為什麼死 |
|---|---|
| 讀出圖片網址給 `curl` 下載 | 網址同源 + 需要 cookie；擴充功能也會擋住含 query string 的網址 |
| 頁面 fetch → POST 到本機接收器 | `chatgpt.com` 的 CSP `connect-src` 擋掉連本機 |
| ~~用 `file_upload` 傳檔案給 ChatGPT~~ | **這條之前是錯的。2026-08-20 實測可行**，前提是檔案要放在本 session 的 scratchpad |

細節與可直接貼的程式碼在 [`snippets/chatgpt-dom.md`](snippets/chatgpt-dom.md)。

## 八、一輪的完整流程（新版）

```
① 你說要做什麼遊戲
      ↓
② 我開一個 ChatGPT Project，設 Instructions，把 project-resources/ 六份文件推進 Sources
      ↓
③ 我指定引擎（3D 立牌 or 2D 橫捲）與素材預算（N 張、M 批）—— GPT 不自己選
      ↓
④ 「做企劃」→ 企劃書 → blob 下載 → 存成 遊戲N/plan.md → 推回 Sources
      ↓  ★ 你在這裡看一次，點頭再往下
⑤ 「做場景設計」→ 同樣存回 repo + 推回 Sources
      ↓
⑥ 「做設定圖」→ 角色 REF001~、場景 REF101~ → 下載 → 推進 Sources
      ↓  ★ 你在這裡看一次造型，不喜歡就重生（這一步重生最划算，後面十幾張全靠它）
⑦ 「做素材清單」→ 我轉成 assets.json → asset-list-source.ps1 → 推回 Sources
      ↓
⑧ 【自動迴圈】每批 6~8 張，同一個對話連續生，prompt 一律引用設定圖
      ↓
⑨ ingest.ps1 → build.ps1 → qa.ps1 → _contact.jpg
      ↓
⑩ 我先看一次 contact sheet，明顯壞的自己重生，不打擾你
      ↓  ★ 你看 contact sheet 驗收
⑪ 我接進 index.html、改版號、根目錄選單 +1
      ↓
⑫ 你在電視上實際玩過每一關（截開場畫面看不出疊圖與引導錯誤）
```

**批次為什麼是 6~8 張？** 一批一個對話，批內連續生 → 模型看得到自己前面生的圖，一致性最好
（前 5~8 張很穩，之後開始漂；實測第 6 張把破壞球畫成水泥車）。超過就換新對話重開一批。

## 九、自動化等級與自動降級

| 級別 | 誰做什麼 | 什麼時候用 |
|---|---|---|
| **L3 全自動** | 我從送 prompt 到下載全包 | 預設 |
| **L2 半自動** | 我送 prompt + 等生成，**下載鈕交給你點** | L3 的下載環節連兩批失敗時自動降到這裡 |
| **L1 只產 prompt** | 我產出可複製的 prompt 清單，你自己貼自己載 | ChatGPT 改版把自動化整個打壞時的保底 |

**後半段（ingest → build → qa → 接線 → 版號）完全共用**，降級只會多花你幾分鐘。

### L3 最可能的失敗點（照痛感排序）

1. **靜默抓錯圖**（痛感最高）——抓到上一輪的舊圖或縮圖，一路綠燈到遊戲畫面糊掉才發現。
   → 落地時硬性驗：檔案寫完整、短邊 ≥900px、長寬比符合宣告值 ±8%、sha256 與上一張不同。**這道閘門不能省。**
2. **生圖額度限流**（機率最高）——30 張素材不可能一天做完。
   → 狀態由檔案系統表達（`_raw/` 裡有沒有那個檔），中斷後續跑不重生已有的圖。
3. **Chrome 下載提示**——第一次會問「這個網站想下載多個檔案」，按一次**允許**。
4. **ChatGPT 改版**——定位一律用 `aria-label` / `data-testid` / `alt`，不用 class；每批開跑前先探測一次。

## 十、QA 的校準原則（這條最容易做錯）

`tools/qa.ps1` 能量 20 幾項指標，但**閾值不可以照理想規格訂**：

> 用理想規格跑遊戲8 現有 32 張素材 → **3 FAIL / 23 WARN**。
> 但這 32 張已經上線、小孩已經在玩、你已經批准了。
> **對驗收系統而言，人已批准的產出就是標準答案。**
> 一個對標準答案給出 81% 不通過的系統，量到的不是品質問題，是「規格訂得比現實嚴」。

**校準規則：現有 32 張必須全數 PASS。**

| 檢查 | 原閾值 | 改成 | 原因 |
|---|---|---|---|
| 內容佔比過小 | 0.76~0.90 | 0.65~0.95 | CHAR005/011 現役素材會被殺 |
| 偏離中心 | 0.44~0.56 | 0.40~0.60 | CHAR003 會被殺 |
| 基準線偏移 | 0.03~0.10 | **整條刪掉** | 遊戲端 `measurePads()` 已完全補償 |
| 碎片偵測 | 0.01 | **整條刪掉** | CHAR007 的「碎片」是翻滾的塵土，那正是小孩最愛的搞笑失敗動畫 |
| 畫風漂移 | 直方圖距離 0.72 | **降成 warn** | 同角色不同姿勢實測 0.31~0.68，安全邊際只有 0.04 |

> 誤殺的代價是**燒生圖額度**：一張圖同時觸發 5 條檢查 → 重試 4 次 → blocked。
> 12 張角色 × 4 次 = 48 次生圖全部白燒。這不是理論風險，是照理想閾值必然發生的事。
