# 🎨 素材工作流：Claude 做遊戲 ＋ ChatGPT 產素材圖

> 文件產生日期：2026-08-18
> 目標：**新增一款遊戲時，素材從發想到進遊戲全自動**，你只需要看一張總覽圖說「好」或「這張重生」。

---

## 一、分工

```
你          ：說「我要做一款 XXX 遊戲」→ 最後看一張 contact sheet 驗收 → 玩
Claude（我）：寫規格 → 寫 prompt → 開瀏覽器操作 ChatGPT → 下載 → 去背/正規化 → QA → 接進遊戲 → 改版號
ChatGPT     ：只做一件事——照 prompt 生圖。不負責去背、不負責裁切、不負責命名
```

**為什麼 ChatGPT 只負責生圖？**
它的 Python 沙盒確實能幫忙去背裁切（`Game007` 的舊對話就是這樣做的），但那是**每次都要重講一遍、結果不可重現**的做法。
去背/裁切/對齊是純機械運算，放本機 PowerShell 才能版本控制、才能改一次參數整批重跑、而且**不燒生圖額度**。

## 二、已實測的機制（2026-08-18 在真實頁面上跑過）

### ✅ 可行

| 機制 | 做法 | 實測結果 |
|---|---|---|
| 進專案開新對話 | `navigate` 到 `chatgpt.com/g/g-p-<id>-<slug>/project`，直接在輸入框送出 | 自動在專案底下開新對話 |
| 灌入長 prompt | `document.execCommand('insertText', …)` 對 `#prompt-textarea` | 38 字中文含換行完整灌入，**不會誤觸送出** |
| 送出 | `[data-testid="send-button"].click()` | — |
| 判斷還在生成 | `[data-testid="stop-button"]` 存不存在 | 最可靠的訊號 |
| 找到生成的圖 | 最後一則 `[data-message-author-role="assistant"]` 裡 `naturalWidth ≥ 512` 的 `img` | — |
| **拿到全解析度原圖** | 對話裡的 `<img>` **就是原圖**，不必點開燈箱 | 實測 `naturalWidth=1536, naturalHeight=1024` |
| 取得圖片位元組 | 頁面內 `fetch(img.src, {credentials:'include'})` | `200 image/png 325788 bytes` |
| 存成我指定的檔名 | blob → `<a download="CHAR001.png">` → 落到 `C:\Users\id753\Downloads\` | 檔名完全由我控制，**Chrome 一次都沒跳詢問** |
| 壓成 WebP | `ffmpeg -c:v libwebp -quality 80` | **省 88~92%**，且 alpha 通道 PSNR = `inf`（libwebp 預設無損壓 alpha）。遊戲7 第一批 7 張：PNG 4.87MB → WebP 400KB |

### 🔁 實跑後才發現的（靜態探勘會寫錯的地方）

| 以為 | 實際 |
|---|---|
| 用 `ref` 或座標點按鈕 | **會靜默失敗**。一律用 JS `.click()` |
| 生成的圖在 assistant 訊息容器裡 | **不在**。要全域找 `img[alt^="Generated image"]` |
| 抓到 img 元素就能讀圖 | 圖是 **lazy-load**，要先 `scrollIntoView()` + `loading='eager'`，否則 `naturalWidth` 永遠是 0 |
| 數「有幾張圖」判斷進度 | 對話**虛擬捲動**會把圖移出 DOM，數量會忽多忽少。要看「最後一張的 alt」 |
| 停止鍵消失 = 圖好了 | 不是。還要 `naturalWidth >= 512` 才算完成 |
| 送出後輸入框會清空 | **不會**，下一次注入會疊成兩段。每次送出後要強制清 |
| 送出鈕存在 = 送出成功 | 生成中它會被換成停止鍵，查了會拿到 null 造成假陰性 |
| `javascript_tool` 可以在頁面裡等到好 | 有 **45 秒硬逾時**，頁面內等待要壓在 20 秒內，且每步都要能重入 |

### ❌ 不可行（試過，死路）

| 想做的事 | 為什麼死 |
|---|---|
| 讀出圖片網址給 `curl` / `Invoke-WebRequest` 下載 | 網址是 `chatgpt.com/backend-api/estuary/content?…&sig=…`，**同源 + 需要 cookie**；而且擴充功能會擋住把含 query string 的網址回傳給我（`[BLOCKED: Cookie/query string data]`） |
| 頁面 fetch 圖片 → POST 到本機接收器 → 直接寫進專案資料夾 | **`chatgpt.com` 的 CSP `connect-src` 擋掉連本機**。實測 `TypeError: Failed to fetch`，本機伺服器（Node，`http://127.0.0.1:9911`，同一支 `curl` 打得通）完全收不到封包 |
| 用 `file_upload` 把專案裡的參考圖傳給 ChatGPT | 工具只接受「使用者分享給本 session 的檔案」，專案路徑**很可能被拒**（未實測）→ 所以一致性改用「一批一個對話、批內連續生」處理，不靠上傳 |

**結論：唯一可行的取圖路徑是「瀏覽器下載資料夾」**，再用 shell 搬進專案。
細節與可直接貼的程式碼在 [`snippets/chatgpt-dom.md`](snippets/chatgpt-dom.md)，
該檔末尾的「**實跑修正**」章節是跑完遊戲7 第一批之後改寫的，以那份為準（靜態探勘寫錯了三處）。

## 三、這條工作流真正的瓶頸（重要，別搞錯方向）

審查階段實測了遊戲8 現有 32 張素材，結論很清楚：

> **瓶頸不在按鍵次數，在模型畫不準。**

| 量到的事 | 數字 |
|---|---|
| 同角色不同影格「高度佔畫布比例」落差 | **19.8 個百分點**（規格希望 ±3pp） |
| 水平中心飄移 | **8.5pp**（規格希望 ±2pp） |
| 底部基準線落差 | **16.6%** |

而這是在「有附參考圖、同一個 Project、指令寫得很細」的條件下量到的。

**所以：**
- 自動化瀏覽器省下的是「複製貼上與點按」的工 → 值得做，但它**不會讓素材變好**。
- 讓素材真的能用的是本機的 **`build.ps1` 幾何正規化**（統一尺度 → 統一水平中心 → 統一底線）。
  這是 prompt 永遠做不到、而程式 100% 做得到的事，**是整套工作流最有價值的一塊**。
- 最後的「好不好看」交給人眼看一張 contact sheet，一次批准整批。

## 五、一輪的完整流程

```
① 你說要做什麼遊戲
      ↓
② 我寫 plan.md（沿用遊戲7/8 的規格書格式）+ assets.json 素材清單
      ↓
③ 我在 ChatGPT 開一個 Project，貼上 project-instructions.md 的指令
      ↓
④ 【自動迴圈】每一批 6~8 張，同一個對話連續生：
      灌 prompt → 送出 → 每 8 秒探一次狀態 → 圖出現 → blob 下載成 {ID}.png
      ↓
⑤ ingest.ps1：Downloads 快照 diff → 依修改時間對回批次順序 → 搬進 pic/_raw/
      ↓
⑥ build.ps1：有 alpha 走 knee / 沒 alpha 走去棋盤格 → 翻轉裁切 → 縮到目標尺寸
             → 同一組影格跑幾何正規化（統一尺度 + 中心 + 底線）→ pic/opt/
      ↓
⑦ qa.ps1：量測 + 拼出 _contact.jpg
      ↓
⑧ 我先看一次 contact sheet（我看得到圖），明顯壞的自己重生，不打擾你
      ↓
⑨ 你看 contact sheet 驗收 → 說「好」或「第 3 張重生」
      ↓
⑩ 我接進 index.html 的 IMG_LIST、GAME_VER +1、根目錄選單 ver +1
      ↓
⑪ 你在電視上實際玩一次（contact sheet 看不出跑步動畫會不會抖）
```

**批次為什麼是 6~8 張？**
一批一個對話，批內連續生 → ChatGPT 看得到自己前面生的圖，一致性最好（前 5~8 張很穩，之後開始漂）。
超過就換新對話重開一批，跨批的不一致交給 `build.ps1` 正規化 + 人眼挑。

## 六、自動化等級與自動降級

你要的是 **L3 全自動**，機制上（第二節）確認做得到。但要誠實講風險，所以設計成**會自己降級**：

| 級別 | 誰做什麼 | 什麼時候用 |
|---|---|---|
| **L3 全自動** | 我從送 prompt 到下載全包 | 預設。這是目標 |
| **L2 半自動** | 我送 prompt + 等生成，**下載鈕交給你點**（一批 8 次，30 秒） | L3 的下載環節連兩批失敗時自動降到這裡 |
| **L1 只產 prompt** | 我產出一份可複製的 prompt 清單，你自己貼自己載，我接手處理 | ChatGPT 改版把自動化整個打壞時的保底 |

**三個等級的後半段（ingest → build → qa → 接線 → 版號）完全共用**，所以降級只會多花你幾分鐘，不會白做工。

### L3 最可能的失敗點（照痛感排序）

1. **靜默抓錯圖**（痛感最高）——抓到上一輪的舊圖或縮圖，一路綠燈到遊戲畫面糊掉才發現。
   → 落地時硬性驗三件事：檔案寫完整、短邊 ≥900px、長寬比符合宣告值 ±8%、sha256 與上一張不同。**這道閘門不能省。**
2. **生圖額度限流**（機率最高）——30 張素材不可能一天做完。
   → 狀態直接由檔案系統表達（`_raw/` 裡有沒有那個檔），中斷後續跑不重生已有的圖，不燒額度。
3. **Chrome 下載提示**——第一次會跳「這個網站想下載多個檔案」，你按一次**允許**，之後不再問。
4. **ChatGPT 改版**——所有定位都用 `aria-label` / `data-testid` / `alt`，不用 class；每批開跑前先做一次探測。

## 七、QA 的校準原則（這條最容易做錯）

`tools/qa.ps1`（833 行，已寫好）能量 20 幾項指標。但**閾值不可以照理想規格訂**：

> 用理想規格跑遊戲8 現有 32 張素材 → **3 FAIL / 23 WARN**。
> 但這 32 張已經上線、已經在 GitHub Pages 上、小孩已經在玩、你已經批准了。
> **對驗收系統而言，人已批准的產出就是標準答案。** 一個對標準答案給出 81% 不通過的系統，
> 量到的不是品質問題，是「規格訂得比現實嚴」。

**校準規則：現有 32 張必須全數 PASS。** 具體修正：

| 檢查 | 原閾值 | 改成 | 原因 |
|---|---|---|---|
| 內容佔比過小 | 0.76~0.90 | 0.65~0.95 | CHAR005/011 現役素材會被殺 |
| 偏離中心 | 0.44~0.56 | 0.40~0.60 | CHAR003 會被殺 |
| 基準線偏移 | 0.03~0.10 | **整條刪掉** | 遊戲端 `measurePads()` 已經完全補償了 |
| 碎片偵測 | 0.01 | **整條刪掉** | CHAR007 的 16 個「碎片」是翻滾的塵土，CHAR010 的是英雄星星——那是刻意畫的美術，而且塵土正是小孩最愛的搞笑失敗動畫 |
| 畫風漂移 | 色彩直方圖距離 0.72 | **降成 warn，永不觸發重生** | 同角色不同姿勢實測 0.31~0.68，安全邊際只有 0.04。換個姿勢顏色分布本來就會變 |

**只留 6 條 fail 級**：空圖、去背整個失敗、主體被畫布切到、檔案 >500KB、同組影格正規化後仍不齊（代表 build 有 bug）、地面拼接圖邊緣軟掉。
其餘全部降 warn，只印在 contact sheet 的標題列給人眼參考。

> 誤殺的代價是**燒生圖額度**：一張圖同時觸發 5 條檢查 → 重試 4 次 → blocked。
> 12 張角色 × 4 次 = 48 次生圖全部白燒，一張都拿不到。這不是理論風險，是照理想閾值必然發生的事。

## 八、還沒實測、第一次跑要當場確認的事

| # | 待確認 | 失敗時的退路 |
|---|---|---|
| 1 | blob `<a download>` 會不會被 Chrome 擋 | 改點 ChatGPT 自己的下載鈕 |
| 2 | ChatGPT 交出來的是 PNG 還是 WebP | 本機轉檔（`System.Drawing` 不支援 webp，要另找工具）——**不要判失敗**，Downloads 快照 diff 要比對**所有副檔名**，只比 `.png` 會漏掉 |

| 5 | `file_upload` 能不能傳專案裡的圖 | 不能就完全不靠上傳，用「批內連續生」維持一致性 |

1. 在 Chrome 登入 ChatGPT（已確認：Plus，登入中）。

5. 跑批次的那 15~20 分鐘，**不要動那個分頁**（打字會搶走輸入框焦點）。

## 十、實戰紀錄：遊戲7 美化（2026-08-18）

第一次完整跑完整條工作流的結果，數字都是實測的。

| 項目 | 數字 |
|---|---|
| 生圖次數 | 14 次（含 2 次重生） |
| 成品素材 | 11 張，**共 400KB**（同樣內容存 PNG 是 4.87MB） |
| 一次過關率 | 12/14。重生的兩張：媽祖被模型自己加了背光圈與雲朵、雲是白底白物去背失敗 |
| 背景真透明 | **11 張裡只有 1 張**。其餘棋盤格 3、純色底 7 |
| 輸出尺寸 | 1024×1536 / 1536×1024 / 1402×1122 / 1254×1254 / 1983×793 都出現過 |
| 單張耗時 | 生圖 40~90 秒 |
| 程式改動 | 6 個 `CanvasTexture` 單例換成 `imgTex()`、4 處環境元素替換、3 處每幀 scale 補長寬比 |

**做法**：素材接在新檔 `index-新美術.html`，原本的 `index.html` 一個字都沒改，
根目錄選單同時列出「蓋廟大作戰」與「蓋廟大作戰（新美術）」，隨時可以對照或退回。

**第三批（小師傅 + 工程車）後來做了。** 我原本建議不做，使用者決定要做——但改用了不會讓遊戲變差的作法：
不是「換成靜態 2D 圖」，而是**把動畫語意搬進影格**。
- 小師傅四影格：蹲下不再靠 `scale.y` 壓扁，蹲姿本身就畫在圖裡（更好看），仍保留 0.94 輕微壓縮維持回饋。
  觸控模式原本沒有蹲下回饋，現在按住就會蹲，比原版好。
- 挖土機兩影格：`exArm.rotation.z` 的 -0.2↔-0.9 兩段 lerp 剛好對應兩張圖。
- 破壞車拆成「車體」＋「鐵球」兩張，鐘擺數學完整保留（那是全遊戲最好笑的地方）。
- **誠實捨棄**水泥車與壓路機的滾筒旋轉——2D 真的做不到，但它只是裝飾不是玩法回饋。

**刻意沒做的**：**地面／廟埕的無縫平鋪 tile**。AI 生不出真正無縫的貼圖，大面積地板上接縫會很明顯，
維持原本的純色 `MeshToonMaterial` 反而乾淨。

## 十一、三方分工（2026-08-18 確立）

| 誰 | 負責 |
|---|---|
| **ChatGPT**（Plus） | 美術素材、背景音 |
| **Claude**（我） | 寫程式、驅動瀏覽器、後處理、接線、驗收 |
| **Gemini**（AI Pro） | TTS 語音 |

> Gemini 那條線的注意事項：20 USD 的 Google AI Pro 給的是 Gemini App / Veo / NotebookLM，
> **Gemini App 本身沒有「輸入文字→下載語音檔」的功能**，NotebookLM 的語音導覽是雙人 podcast 形式，
> 不能拿來當遊戲語音。要用的是 **Google AI Studio 的 TTS**（可指定語者、控制語氣、下載音檔），
> 那是走 API/AI Studio 這條線、與訂閱分開計費。**這段尚未實地驗證過**，第一次要用時先開瀏覽器確認。
>
> 好消息是遊戲8 的 `mic/s1~s18.mp3 + 對照.txt` 已經是「預先產好音檔」的架構，TTS 產物可以直接套進去。

## 十二、一句話

> 自動化拿掉的是「貼 prompt、點下載、改檔名、去背、接線、改版號」這些工；
> 拿不掉的是「模型畫不準」——那由本機幾何正規化解決，最後的好不好看由你看一張圖決定。
