# 02 場景與技術約束

這份文件講「程式端做得到什麼」。你設計畫面與場景時，只能設計程式畫得出來的東西；設計超出這個範圍，素材就會做出來卻用不上。

---

## 1. 技術棧：兩種引擎，同一種思維

> **開工前先確認你要用哪一種。** 引擎由 Claude 在**階段 0** 指定（見 00）。
> 這一節兩種都寫，是為了讓你知道差別——**實際設計時只照被指定的那一種交，不要兩種都寫**。
> 3D 要交的是立牌的前後排列與堆疊槽位；2D 要交的是視差層速度與可左右接續的橫幅，形狀完全不同。
> 沒收到指定就直接問，不要自己選。

- 每款遊戲是**一個單獨的 HTML 檔**，沒有遊戲引擎編輯器、沒有場景檔、沒有骨架動畫系統。
- 目前兩種實作並存：
  - **Three.js 3D 場景**（遊戲4～7）：素材是 **Sprite 立牌（billboard，永遠正面朝鏡頭）**，靠 z 座標前後排列做縱深。
  - **2D Canvas 橫向捲軸**（遊戲1～3、遊戲8）：素材是 `drawImage` 貼上去的圖層，靠多層不同速度捲動做縱深（遊戲8 是四段：遠景 0.18、中景 0.5、地面 1.0、前景草叢 1.15）。
- **兩種都不是 3D 模型。** 素材永遠是一張平面圖，只是被擺在不同深度。
- 補充：遊戲7 的 AI 素材接在 `index-新美術.html`，原本手繪版的 `index.html` 完全沒動，兩個版本在選單並存。

## 2. 唯一正確的心智模型：舞台佈景片

把畫面想成**紙板劇場**：每張圖是一片立起來的佈景板，前後排幾層，鏡頭幾乎正對著看。

- **一個元素 = 一張圖。** 會分別移動、分別縮放、分別出現的東西，就必須是分開的圖 — 程式只能整張圖一起搬。
  - 實例：遊戲7 的破壞車拆成「車體」＋「鐵球」兩張，鐘擺數學才保得住（那是全遊戲最好笑的地方）。
- **不要把兩個元素畫在同一張圖裡**（除非它們永遠一起動），否則程式無法讓其中一個單獨動作。
- **不要畫地面、不要畫背景、不要畫投影陰影。** 地面是場景的一層，落地陰影由程式畫橢圓（遊戲8 用 `rgba(60,40,20,.25~.30)` 的橢圓，玩家與障礙各一顆），素材自帶陰影會在深色底上露出灰塊。

## 3. 正面平視是硬性要求

- 立牌**轉不了身**，鏡頭永遠看到同一面，所以 3/4 斜角的圖擺進場景會「站歪」。
- 遊戲7 的相機幾乎是平視：相機在 y=4.7、看向 y=2.45，水平距離約 16 個世界單位，**俯角只有 8° 左右**（程式註解裡寫的 7.4° 是鏡頭拉近前的舊值）。正面立面圖才貼得合。
- **會被程式堆疊組裝的東西要求最嚴**：遊戲7 的廟是台基 → 台階 → 後牆 → 匾額 → 柱 → 橫樑 → 屋頂 → 神龕台座 → 燈籠 → 神像逐件疊上去的，槽位寫死在程式裡，只要有一件是斜角的，整座廟就對不齊。這類零件請明確標「正面平視立面圖，兩端畫成平的切面、不要透視收窄」。
- **⛔ 禁令：堆疊建築的順序與槽位是寫死的，企劃與場景設計不得出現「玩家自選要蓋哪些部件」或「每局隨機組合出不同建築」。**
  遊戲7 的十件是固定順序、固定槽位、寫死的座標。自由組裝對 4 歲很有吸引力，但對程式是組合爆炸——
  每多一種組合就要多一套槽位座標與堆疊順序。要有變化，改用**換色**（見第 7 節）或換裝飾，不要換結構。
- **堆疊零件會被強制拉伸**：廟宇零件在程式裡一律被拉成固定的幾何尺寸，不照 AI 圖的原始長寬比（因為對不齊比被拉寬更礙眼）。所以這類零件的構圖比例要接近目標形狀 — 橫樑要很扁、柱子要很細長 — 差太多會被拉變形。
- **非堆疊的立牌則相反**：它們的長寬比是寫死在程式的 AR 表裡（Sprite 的 scale 不會自動照圖片比例），換素材要重算。所以同一個元素改版時，盡量維持原本的長寬比。
- 例外：**要躺平被俯視的面**（地面貼圖、工作台頂面）不能用立牌，程式改用躺平的平面 — 這種要標「**俯視角**」，並在交付清單裡註明它是躺平的層。

## 4. 電視上很小：靠剪影，不靠細節

畫面最後是手機投影到電視，元素在畫面上都很小。遊戲8 程式端的實際渲染尺寸：

| 元素 | 在電視畫面上的高度佔比 |
|---|---|
| 主角 | 34% |
| 中景樹 | 36% |
| 地面帶 | 21.5% |
| 松果道具 | 7% |
| 裝飾小鳥 | 4.4% |

> 這一欄是**元素在螢幕上的大小**，是程式的排版數字，**不是素材畫布的規格**。
> 素材本身的畫布尺寸、主體佔畫布的高度比例、水平置中誤差、底部基準線一律不要寫進 prompt——
> 實測服從率接近 0（理由見 **03 第四節**）。

- **一個 7% 高的東西只剩剪影。** 造型要簡化、輪廓要好認、與背景要有高對比。
- 細節不要過碎：碎小的花紋、細線、小字在電視上會糊成一團雜點。
- 4 歲的小玩家要在半秒內認出「這是可以吃的」「這是要閃的」，靠的是形狀與顏色差異，不是質感。

## 5. 程式做得到的動態（可以放心設計）

| 能力 | 說明 |
|---|---|
| 位移 | 任意方向移動、跟隨、彈跳、視差捲動 |
| 縮放 | 整張圖等比或非等比縮放（遊戲7 青蛙被壓路機壓扁就是把高度壓到 0.18、寬度拉到 1.35） |
| 旋轉 | 整張圖繞中心旋轉（翻滾、搖曳、鐘擺） |
| 透明度 | 淡入淡出、閃爍無敵、殘影拖尾 |
| 水平鏡像 | 左右翻面（遊戲8 的小鳥素材面向左，往右飛時才翻轉） |
| 影格切換 | 多張圖輪播成動畫（遊戲8 跑步 4 影格、兩隻小狗各 2 影格拍手；遊戲7 小師傅 4 影格） |
| 整片染色 | `material.color` / 疊色會**乘上**貼圖，可以把同一張圖每局換成不同顏色 |
| 程式自畫的光效 | 光暈、放射漸層、粒子、文字都由程式畫，素材不用自帶 |

## 6. 程式做不到，或代價太高（不要設計）

- **真正無縫平鋪的地面／牆面貼圖**：AI 生不出無縫，大面積會看到接縫。遊戲7 因此**刻意不做**地面 tile，改成「一整張不重複的圖鋪滿鏡頭看得到的範圍、四周在 build 時做 alpha 羽化，融進下面那片純色平面」；遊戲8 的地面帶與遠景森林則是靠「裁掉來源圖左右各 8px 半透明邊 ＋ 奇數塊左右鏡像」才拼得起來。要橫向重複的長條，請設計成**兩端平淡、鏡像可對接**的圖，並在清單裡註明「會被鏡像拼接」。
- **立牌的側面與轉身**：只能水平鏡像，不能「轉過去看到背面」。所以角色一律面向同一側，身上**不要有左右不對稱的標誌或文字**，翻轉後會穿幫。
- **素材內部的局部變形**：不能讓圖裡的一隻手單獨舉起來、一根柱子單獨彎曲。要動就切成兩張圖，或多影格。
- **真正的互相咬合遮蔽**：立牌之間只有前後順序，角色「繞到柱子後面再繞回來」這種穿插很容易穿幫，別當成玩法。
- **3D 光影**：素材上的光要畫死（統一柔和頂光），場景不會替它算陰影。

## 7. 需要每局換色的東西，畫成中性灰白

- 染色是**相乘**：灰白 × 紅 = 紅，但**彩色 × 紅 = 髒色**。所以只要程式要換色，素材就必須是**淺灰白中性色，完全不上彩**。
- 實例：遊戲7 的柱子與台基每局從 5 組配色隨機抽（那是刻意的重玩性設計），素材就畫成灰白；煙塵素材也畫成中性白，程式再染成棕色或灰色。
- 設計時請主動標出：**這個元素每局換色嗎？** 換色就中性灰白，不換色就直接上色。
- 附帶提醒：淺灰白主體**不要畫在白底上**（遊戲7 的台基第一版就是這樣，淺灰白石台跟白底分不開，去背整個吃光只剩幾條線；白雲那張也踩過同一個坑）。淺色主體請在 prompt 裡指定「背景填滿鮮豔的洋紅色純色底」，本機去背走純色分流就分得乾淨。同理，**主體身上不要用洋紅、桃紅、紫色**，會被色鍵誤刪。

## 8. 版面分層與鏡頭構圖

典型分層，由遠到近（遊戲8 實例）：

```
① 天空／遠景森林   視差 0.18 倍速，滿版，奇數塊鏡像拼接
② 空中裝飾         小鳥，各自飄移，半透明
③ 中景樹           視差 0.5 倍速，高度 36%
④ 地面帶           1.0 倍速，地平線在畫面高 80% 處
⑤ 工作區／玩法層   玩家、障礙、道具（玩家固定在畫面寬 24% 處）
⑥ 前景草叢         1.15 倍速，畫面最下緣，只露一截
```

遊戲7（3D）對應層：天空色＋霧 → 遠山橫幅 → 背景聚落小廟 → 地面／工作台 → 廟本體（逐件堆疊）→ 工程車與角色 → 畫面角落的常駐助手（關掉深度測試，永不被遮擋）。

構圖鐵則：

- **工作區要夠大。** 遊戲7 的工地台從 9×6 加寬到 15×7.5，就是因為原本只佔畫面寬約 27%，左右各一大片空地，和滿版的遠山比起來像個小盒子。玩法發生的地方是主角，背景是配角。
- **版面要分層、有縱深、元素多元**，避免所有角色擠在同一條水平線上的侷限感。
- 遠景不要搶戲，但也**不要指望程式幫你壓淡**：遊戲7 的遠山是一張立牌，程式沒有替它降飽和，淡不淡完全看圖本身，所以遠景請直接畫成低飽和、低對比、少細節。（會被程式乘一層暖灰壓飽和的是地面貼圖，不是遠山。）
- 天空／地面的大面積留給純色或極簡漸層，畫面的視覺重量放在工作區。

## 9. 場景設計交出來時，要包含這些

**先講清楚交付形式**：場景設計是**文字**，在「設計對話」裡交。這跟「生圖對話」是分開的兩件事 — 生圖對話一律只出圖、不要文字說明。這一節講的是設計對話的輸出格式。

**還有一件事要一起交：場景設定圖。**
同一個場景如果要拆成多層分開生、或要出多個時段版本，先生一張**場景設定圖**（`REF101` 起）當基準——
它定住整體色調、光線方向與遠中近景的色彩層次，之後每一層都引用它。
不這樣做的話，遠山、地面、前景各自生出來的色溫與明度會對不起來，疊起來像四張不同遊戲的圖。
完整流程見 **05**。

每個場景請用這個結構交付（文字即可，不用畫版面圖）：

1. **分層清單**：由遠到近列出每一層，並標明該層是「捲動／靜止」、「立牌／躺平俯視面」。
2. **每層的元素**：列出元素名稱與數量，一個元素一行。
3. **相對大小**：以主角高度為 1，寫出各元素的倍率（例：中景樹 ≈ 2.5、道具 ≈ 0.2）。這些數字是給程式設定用的，**不要寫進生圖 prompt**。
4. **動 / 靜**：哪些會動、怎麼動（位移／縮放／旋轉／淡入淡出／鏡像），對照第 5 節的能力表。
5. **多影格清單**：哪些元素需要幾張影格、每張是什麼動作（例：跑步 4 張、拍手 2 張）。同一組影格要註明「同一組」，批內才會連續生、風格才一致。
6. **染色標記**：哪些元素每局換色（→ 中性灰白），哪些固定上色。
7. **堆疊零件標記**：哪些元素會被程式當積木疊起來（→ 嚴格正面平視、兩端平切、比例接近目標形狀）。
8. **鏡像拼接標記**：哪些是要橫向重複的長條（→ 兩端平淡可對接）。
9. **顏色用文字描述**（「暖灰」「磚紅」「奶油色」），不要寫色碼 — 色碼字串實測會被模型直接畫進圖裡，ID 也一樣。

這份清單會被轉成 `assets.json`：每個元素一筆，欄位是 `id`／`用途`／`比例朝向`／`prompt`／`組`／`輸出`。
`組` 就是上面第 5 點的同組影格；`輸出` 是本機後處理參數，**你一律交空物件 `{}`**（見 04）。
所以上面每一項都有明確去處，寫得越具體越不用回頭補。

檔案大小不用你操心：壓縮在本機做（`build.ps1` 輸出 WebP，實測省 88～92%），驗收門檻依素材類型不同（`qa.ps1` 的 profile 從道具的 160KB 到地面帶的 600KB），而且超標只是警告、不是退件。設計時不必為檔案大小讓步，但也不要設計「一張圖裡塞滿三十個獨立小物件」這種註定要被拆開的東西。
