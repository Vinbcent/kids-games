# 04-素材命名與交付格式

這份文件規範**你（GPT）交出來的東西長什麼樣子**。你的產出會被 Claude 直接讀進本機腳本（`ingest.ps1` / `build.ps1` / `qa.ps1`）與遊戲程式，所以格式必須固定、可機器解析。內容好不好是另一份文件的事；這份只管**形狀**。

三件產出，各有固定格式：**企劃書**（Markdown）、**場景設計**（Markdown）、**素材清單**（JSON）。

---

## 一、素材 ID 命名規則

ID 就是本機檔名。`ingest.ps1` 會把下載到的圖改名成 `pic/_raw/CH101.png`（非 PNG 一律轉成 PNG 入庫），`build.ps1` 後製完輸出 `pic/opt/CH101.webp`，遊戲程式則把這串字寫死在載圖的地方。**兩個英文字母前綴 ＋ 三位數字**，不用底線、不用中文。

| 前綴 | 用途 | 實例（遊戲7 已上線） |
|---|---|---|
| `BG` | 背景、地面、遠景滿版圖 | BG001 遠景山巒橫幅、BG002 地面貼圖 |
| `CH` | 角色（主角、NPC、神像） | CH001 小師傅站立、CH101 媽祖神像 |
| `VH` | 載具、工程車、機具 | VH001 挖土機、VH006 鐵球＋鐵鏈 |
| `TP` | 場景結構物與可堆疊零件 | TP002 燕尾脊屋頂、TP003 紅柱、TP009 竹鷹架 |
| `FX` | 特效粒子、小物、小動物 | FX003 青蛙、FX007 煙塵團、FX009 金色星光 |
| `EV` | 事件／表演型角色與陣列 | EV001 舞龍龍頭、EV002 舞龍龍身節、EV101 舞獅獅頭 |
| `OB` | **障礙物**（要跳過去、要蹲下躲的） | 跑酷／閃避類遊戲用 |
| `IT` | **可拾取道具**（吃的、撿的、收集的） | 收集類遊戲用 |
| `UI` | 介面圖（開場主視覺等，用 HTML `<img>` 不進 3D） | UI001 開場主視覺 |
| `REF` | **設定圖**（角色 `REF001`~、場景 `REF101`~） | 見下方「REF 是特例」 |

> `OB` 與 `IT` 是這次補上的：舊制的 `OBS101` / `ITEM001`（遊戲8）前綴長度不一致，新遊戲一律用兩字母。

### REF 是特例，不算素材

設定圖（`REF001` 角色、`REF101` 場景）**不是遊戲素材**：

- **不列進素材清單**、不進後製、不進 `pic/opt/`、遊戲程式不會載入它。
- **不佔「一批 6~8 張」的額度**，它單獨先生、單獨上傳。
- 它是**唯一允許出現在 prompt 裡的識別碼**（見第二節）。

完整流程見 **05**。

**三位數字：百位＝換一個主體或一個類別，末兩位＝同一個主體的第幾張。**

- 同一個角色的多張影格 → 末兩位連號：`CH001` 站立待機 / `CH002` 蹲下挖地基 / `CH003` 雙手高舉倒水泥 / `CH004` 慶祝歡呼（同一個小師傅）。
- 換一個角色 → 換百位：`CH101` 媽祖、`CH201` 千里眼、`CH301` 順風耳；`EV001` 舞龍、`EV101` 舞獅。
- 百位也可以用來分「類別」：遊戲8 的 `OBS0xx` 是要跳過去的地面障礙、`OBS1xx` 是要蹲下躲的空中障礙。
- 場景零件、道具、特效這種每張各自獨立、不會連播的，就在同一個百位裡從 001 往下編就好（遊戲7 的 `TP001`～`TP010`、`FX001`～`FX014` 都是這樣），不必為每一件換百位。
- 同一台機具拆成兩件用相鄰編號：`VH005` 破壞車車體、`VH006` 鐵球＋鐵鏈。
- **為什麼百位要編對**：本機 `qa.ps1` 用「前綴＋百位」把影格分組，量同組的尺度、水平中心、腳底基準線有沒有飄。
  （目前那組 regex 是寫死的、只認得遊戲8 的舊 ID，新遊戲多半不會觸發到——但百位仍然要編對，那是人眼看驗收總覽圖時的分組依據。）

**其他規定：**

- **編號可以跳號**（遊戲7 就有 TP010 之後直接跳 TP018），補畫新素材往後接即可，不必補滿。
- **既有 ID 絕對不重編、不回收**——檔名已經寫進遊戲的 HTML（遊戲7 是 `index-新美術.html`），改 ID 等於改程式。要換圖就沿用同一個 ID。
- 一個 ID 對一張圖，一張圖對一個 ID。同一張圖被程式多處使用（FX009 星光同時當「放對位置的獎勵」「慶典彩帶」「媽祖賜福」三種特效）也只給一個 ID。
- 遊戲8 用的是 `CHAR001` / `OBS101` / `ITEM001` / `RUN1` 這種舊命名，前綴長度不一（三到四個字母），`RUN` 連數字位數都不固定。那是舊制，**新遊戲一律用兩字母前綴＋三位數字**，不要沿用。

## 二、ID 絕對不可以出現在 prompt 裡（最重要一條）

- prompt 裡**不准出現素材 ID、批號、任何編號、hex 色碼**。實測這些字串會被模型當成「要畫上去的標籤」直接畫進圖裡。顏色一律用文字描述（「亮橘色」「奶油色」「墨綠色」）。
- **唯一的例外是設定圖檔名**（`REF001.png`）：那是引用設定圖的唯一指路方式，沒有它機制就不成立，所以**必須寫**。
  正因為如此，「圖上不可出現任何文字數字」那條不能放寬，落地時要用眼睛確認檔名沒被畫上去。（判準以 **03 第四之二節**為準。）
- prompt 裡**不准要求任何回覆字串**（例如「畫完回覆 DONE」）。那與 Project instructions 最後一行「直接生成圖片就好，不需要文字說明」直接衝突，模型只會挑一個服從而且無法預測挑哪個；完成判定由本機看 DOM 訊號（停止鍵消失 ＋ 圖片 `naturalWidth ≥ 512`）。
- ID 與圖的對應方式：**送出順序 ＝ 下載順序**，由本機 `ingest.ps1` 拿 Downloads 資料夾的快照差集、依檔案修改時間排序對回批次順序。所以你只要**照清單順序一張一張生**，不要跳號生、不要一次補生前面漏的那張。
- 因此素材清單裡 **`id` 與 `prompt` 一定是分開的兩個欄位**。`prompt` 欄的內容必須是「整段複製貼上就能直接送出」的完整句子，不含任何編號、標題、引號、Markdown 符號（`**`、`#`、`-` 都不要）。

## 三、素材清單交付格式（assets.json）

### Schema

```
{
  "遊戲": "遊戲N-名稱",
  "畫風前綴": "整批共用的畫風描述（與 Project instructions 的【畫風】/【題材】同一段文字）",
  "批次": [
    {
      "名稱": "第N批：這批在做什麼",
      "說明": "這批為什麼放在一起、有什麼要注意的",
      "素材": [
        {
          "id": "CH101",
          "用途": "這張圖在遊戲裡是誰、出現在哪、做什麼動作",
          "比例朝向": "視角與朝向（正面／正側面朝右／俯視），構圖用文字寫橫幅、直幅或接近方形",
          "prompt": "可以直接送出的完整生圖句子",
          "組": "必須彼此保持一致的一群圖填同一個組名；單獨出現的可以省略這欄",
          "備註": "美術上的特殊處理與理由（可省略）",
          "輸出": { }
        }
      ]
    }
  ]
}
```

### `組` 到底是什麼

`組` 不是「動畫影格」的同義詞，是「**這幾張必須互相對得起來**」的宣告。

> **誠實說明它現在的效力**：目前**沒有任何腳本讀這個欄位**——`build.ps1` 不讀，`qa.ps1` 也不讀
> （`qa.ps1` 是用寫死的 ID regex 分組，見下一節第 30 行那條）。所以 `組` 現階段的作用是**給人看的**：
> Claude 接線與人眼驗收時靠它知道哪幾張要互相對齊。
> 這不影響你要做的事——**你在生的時候仍然要刻意讓同組的圖配色、比例、造型一致**，
> 因為那是模型端才做得到的事。

- 同一個角色的連播影格一定要同組（小師傅四影格 `組: "小師傅"`）。
- **會同時並排出現在畫面上的一群也要同組**，即使它們不是動畫：遊戲7 的三尊神像 `組: "神像"`、廟宇八個零件 `組: "廟宇"`，尺度不一致會很明顯。
- 形狀差異太大又各自單獨出現的就不編組：龍頭／龍身／獅頭在遊戲7 都沒有 `組`。

### 你填哪些、Claude 填哪些

| 欄位 | 誰填 | 說明 |
|---|---|---|
| `遊戲`、`畫風前綴`、`批次.名稱`、`批次.說明` | **你** | 畫風前綴寫在清單裡是為了清單自己看得懂，不會被逐張接在 prompt 前面送出——Project instructions 已經生效，重複貼只會拉長 prompt |
| `id`、`用途`、`比例朝向`、`prompt`、`組`、`備註` | **你** | 這六欄是你的產出主體 |
| `輸出` | **Claude** | 全部是本機後製參數，要由程式裡的實際尺寸與去背狀況才決定得了。**你一律交空物件 `{}`**，一個欄位都不要填 |

`比例朝向` 只寫**視角與朝向**（正面／正側面朝右／斜上方微俯視／正上方俯視）和**構圖的胖瘦**（橫幅、直幅、接近方形）。
**不要寫畫布尺寸、不要寫像素、不要寫百分比、不要寫「高度佔畫布 82%」「腳底在 94%」這類數字**——理由見 **03 第四節**，一句話版本是這類指令的服從率接近 0，寫了只會稀釋真正有效的描述。

## 四、批次規則

- **一批 6～8 張，一批一個對話，批內連續生。** 模型看得到自己前面生的圖，前 5～8 張一致性最穩，之後畫風開始漂。跨批的不一致交給本機正規化與人眼挑。遊戲7 實際跑成 7 批 45 張，批量 3～10 張都出現過；6～8 是目標值，**超過 8 張一定要拆**。
- 每批都要有**批號＋名稱**（第一批、第二批…），順序就是實際送出的順序。
- **同一個 `組` 的圖必須在同一批**（小師傅四影格、三尊神像、廟宇零件）。一致性最要緊的就是這種會連播或會並排出現的圖。
- **同一批裡的主體不要差太多。** 若某張的主體與前面幾張差異很大，那一張的 prompt 要明確寫一句話把上下文切斷（例如「不要畫任何車輛」）。遊戲7 實際踩過：連續生五張工程車（挖土機兩影格、水泥車、壓路機、破壞車車體）之後接著生鐵球，模型又畫了一台水泥車，整張報廢重生。
- 一個 ID 只能出現在一批裡，不要重複交付。
- 補畫、重生時**只交出那一批的 JSON 片段**，並沿用原 ID。

## 五、企劃書交付格式

一則訊息交出完整 Markdown 全文，標題文字與層級照抄，不要增刪章節（Claude 用標題定位段落）。沒有內容的章節寫「無」。

```
# 遊戲N-<名稱> 企劃
## 一、一句話說明
## 二、玩法核心
### 操作動作
### 一局的流程
### 勝負與結束條件
## 三、難度與挫折控制
## 四、畫面分層
## 五、角色設定
## 六、重玩性設計
## 七、旁白台詞
## 八、素材需求總覽
```

- 「操作動作」寫玩家身體要做什麼（全系列是體感操作，用 MediaPipe Pose 讀骨架，玩家站在電視前面全身入鏡）。
- 「旁白台詞」用表格交，**四欄：編號｜英文旁白（給 TTS 唸）｜中文畫面文字｜播放時機**。
  兩種語言都要給：**語音一律英文**（目的是磨耳朵），**畫面文字一律中文**（給旁邊的大人看）。
  編號用 `s1`、`s2`、`s3`…**不補零**。音檔由 Gemini 另外產出，不在你的工作範圍，你只要交文字與時機。
- 「素材需求總覽」只列 ID ＋ 一句話用途，完整 prompt 留給素材清單。
- 玩家一律寫「小玩家」或「4 歲玩家」，**不要出現任何人的真實姓名**。

## 六、場景設計交付格式

同樣是一則訊息一份完整 Markdown，標題固定。

```
# 遊戲N-<名稱> 場景設計
## 一、畫面分層
### 遠景
### 中景
### 主場
### 前景
### HUD
## 二、各遊戲狀態的畫面
### <狀態名稱>
## 三、色彩與光線
## 四、每局的隨機變化
## 五、素材對應表
```

- 「畫面分層」每層寫：這層有什麼、會不會動、用哪些素材 ID。版面要分層、有縱深、元素多元，不要讓角色全部擠在同一條水平線上。
- 「各遊戲狀態的畫面」每個狀態一個 `###` 小節（開場、遊戲中、成功、失敗、慶祝…），寫版面配置、出現的素材 ID、動態行為。
- 「素材對應表」是一張表：ID ｜ 出現在哪一層 ｜ 什麼時候出現 ｜ 對應企劃書的哪一段。這張表是 Claude 接線時實際照著做的依據。
- **需要每局換色的元素要在表裡標明**。Three.js 的 sprite 材質色會跟貼圖相乘，程式端用 `material.color.setHex()` 染色，所以這種素材的 prompt 必須明講「畫成淺灰白中性色，不要上任何彩色」，否則染不出乾淨的顏色。遊戲7 的紅柱（TP003）與台基（TP006）就是這樣做的——它們每局會從 5 組配色裡隨機換色。

## 七、交出來之前自己檢查

1. 每個 prompt 裡都沒有素材 ID、沒有編號、沒有 hex 色碼、沒有要求回覆任何字串。（設定圖檔名 `REFxxx.png` 是唯一例外，要引用時就要寫。）
2. 每個 prompt 單獨看都完整，不依賴對話上下文（同角色不同影格寫「同一隻 XXX，配色、比例、服裝配件完全一樣」是可以的，遊戲7 與遊戲8 的清單都是這樣寫的）。
3. 每批 6～8 張，同一個 `組` 的圖沒有被拆到不同批。
4. 淺色主體的 prompt 都加了洋紅底那句；要程式染色的素材都寫了「淺灰白中性色」。
5. 所有 `輸出` 都留空 `{}`，一個欄位都沒填。
6. `比例朝向` 裡沒有畫布尺寸、沒有像素、沒有百分比、沒有基準線位置。
7. JSON 可以被直接 parse：沒有註解、沒有尾逗號、沒有包在說明文字裡。
8. 全文沒有任何真實姓名、學校、生日或裝置名稱；提到玩家一律寫「小玩家」。

## 八、素材清單定稿後會變成一份獨立的 Sources 資源

清單交出來、Claude 轉成 `assets.json` 之後，會再自動轉成一份 **`<代號>-素材清單.md`** 上傳到本專案的 Sources。

**為什麼要獨立一份：**
你每次只生一張圖，沒有全域視野。有了這份資源，你在任何一個新對話裡都撈得到
「這張在整體規劃的哪個位置、屬於哪一批、要跟誰保持一致」。實測 Sources 會被自動檢索，
不用指名檔名也問得到。

**它裡面有什麼、沒有什麼：**

| 有 | 沒有 |
|---|---|
| 全案畫風 | `輸出` 那些後製參數（與你無關） |
| 每一批的名稱與說明 | 本機檔案路徑 |
| 每張的 `id`、`用途`、`構圖/朝向`、`一致性組`、`畫面內容` | — |

**使用規則：**

1. 我說「生 X」時，就照清單裡 X 的「畫面內容」生，不用我再貼一次。
2. 同一個「一致性組」的圖要一次連續生完。
3. 清單裡沒有的東西不要自己加。
4. **清單有更新時我會整份換掉**——Sources 不能編輯，只能刪掉重傳。所以**永遠以最新那份為準**，
   不要沿用舊對話裡的版本。
