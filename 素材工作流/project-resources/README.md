# project-resources：要推進 ChatGPT Project「Sources」的通用文件

> **repo 是唯一真相。** Sources 只是這裡的一份投影。
> 因為 ChatGPT 的 Source **不能改名、不能編輯**（每一列只有 `Download` / `Delete`），
> 所以規格一律在這裡改，改完整份重推；**不要在 ChatGPT 上直接改內容**。

---

## 這裡有什麼

| 檔案 | 給 GPT 讀的內容 |
|---|---|
| `00-專案總則與分工.md` | 專案是什麼、三方分工、階段 0~4 的交付物、文件索引 |
| `01-玩家與企劃約束.md` | 體感訊號白名單／黑名單、4 歲玩家的硬限制、企劃自我檢查 |
| `02-場景與技術約束.md` | 程式端做得到什麼、堆疊建築的禁令、分層構圖 |
| `03-美術規範與已知失敗模式.md` | 每張圖的規範、去背友善規則、fail 清單、**為什麼不寫幾何規格（唯一完整說明）** |

| `05-設定圖流程（角色與場景）.md` | REF 設定圖怎麼生、怎麼引用、它解決與不解決什麼 |
| `_審查紀錄.md` | **不要上傳**。當初這疊文件的完整性批判報告，留作改版依據 |

以 `_` 開頭的檔案是內部紀錄，不推上去。

每款遊戲另外還有三份**專屬**資源（不在這個資料夾，是從各遊戲產生的）：

- `<代號>-企劃書.md`、`<代號>-場景設計.md`：GPT 產出後存回 repo 再推回 Sources
- `<代號>-素材清單.md`：由 `../tools/asset-list-source.ps1` 從該遊戲的 `assets.json` 產生
- `REF001.png` / `REF101.png`…：角色與場景設定圖

## 怎麼推上去

**檔案不經過瀏覽器 JS，直接上傳，檔名原封保留。**

```
1. 把要推的 .md（或 REF*.png）複製到本 session 的 scratchpad 目錄
   —— file_upload 只收「使用者分享給本 session」的路徑，專案資料夾原路徑會被拒
2. 在 Project 頁面點 Sources 分頁（button[role=tab]，要先 pointerdown 再 click）
3. 點 Add sources
4. 用 find 工具拿到 dialog 裡那個 input[type=file] 的 ref
5. file_upload({ paths: [...], ref, tabId })   ← 單次總量 < 10 MB
```

選單裡的另外兩個入口，**不要用來放這些文件**：

- `Add from library`：檔名會變成圖庫自動取的英文標題，而且**改不掉**，prompt 就指不準。
- `Text input`：可以貼長文（欄位沒有長度上限），但內容得整份塞進工具呼叫，而且真相會散在操作紀錄裡。留給臨時的短東西。

完整的 selector 與實測細節在 [`../snippets/chatgpt-dom.md`](../snippets/chatgpt-dom.md) 的 V~AF 章節。

---

## 更新規格時

1. 在這裡改。
2. 到 Project 的 Sources 把**舊的那一份刪掉**（`Source actions → Delete`）。
   > `Delete` 不可逆，**自動化腳本不要自己按**——要刪先跟使用者確認，或請使用者自己點。
3. 重新上傳新的。

## 兩條寫作紀律

**1. 隱私**：這些文件會上傳到外部服務。
不可以出現小孩真名、學校、班級、生日、裝置名稱——一律寫「小玩家」或「4 歲玩家」。
每次改完跑一次：

```bash
grep -rniE "dylan|中班|生日|幼兒園" *.md
```

**2. 只寫模型真的做得到的事**。
幾何規格（高度佔畫布幾 %、置中誤差、腳底位置、畫布尺寸）的服從率接近 0，
寫進去只會稀釋真正有效的規則。完整論證**只放在 `03` 一處**，其他五份都用一句話指過去——
同一段論證抄五遍，遲早會抄歪成互相矛盾的版本（上一版就是這樣壞的，見 `_審查紀錄.md`）。
