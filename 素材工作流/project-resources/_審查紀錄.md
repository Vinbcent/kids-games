# 完整性批判報告：ChatGPT Project Sources（6 份）

**結論先講**：GPT 拿到這疊文件**做不出一份可執行的企劃**。不是因為寫得不夠多，而是因為（a）開工的第一個決策點就沒有答案，（b）全疊最常被重複的那條規則的理由是假的，（c）真正會讓 4 歲玩不了的失敗模式反而沒寫成禁令。

以下四節的技術主張我都對 `素材工作流/tools/build.ps1`、`qa.ps1` 實地查證過，不是從文件推的。

## 一、缺什麼

**1. 這款遊戲是 2D Canvas 還是 Three.js，沒有人決定 — 場景設計無法開工**
`02 §1` 只說「兩種實作並存」（遊戲4～7 是 3D、1～3 與 8 是 2D），`02 §8` 直接給了兩套完全不同的分層範例。但沒有任何一份文件說**新遊戲用哪一種、由誰決定、什麼時候決定**。這不是細節：2D 要交的是視差層速度與可鏡像拼接橫幅（`02 §8 ①④⑥`），3D 要交的是立牌 z 排序與堆疊槽位零件（`02 §3`）。而 `04 §6` 規定的場景設計骨架（遠景／中景／主場／前景／HUD）是 2D 的形狀，套到 3D 遊戲會有一半章節寫不出東西。GPT 在階段 2 的第一行就必須回頭問人。

**2. 角色設定圖流程（05）沒有掛進主流程，GPT 依 00 走永遠不會做它**
`00 §3` 的四階段（企劃→場景→素材清單→生圖）完全沒提設定圖。但 `05 §1` 的觸發條件是「角色有兩個以上姿勢或影格」——幾乎每款都成立。而且 `04 §3` 的 `assets.json` schema 沒有 `REF` 的容身處（它不是素材、不進 build），GPT 交清單時不知道該不該列它、`REF001` 算不算佔掉 `04 §4` 那「一批 6～8 張」的額度。缺的是 `00 §3` 的一個階段 3.5，以及 `04 §1` 前綴表裡的 `REF` 條目。

**3. 「背景音」被指派了，但沒有任何規格 — 而且同一列自己打自己**
`00 §2` 分工表把「背景音」列進 ChatGPT 的職責，同一列右欄的「交界」卻寫「交出**設計文件與圖檔**就結束」。`00 §3` 的四階段、`04` 的三種交付格式，都沒有任何音訊產物。GPT 也產不了音檔。這三個字要嘛刪掉，要嘛補一節說清楚交什麼（幾軌、幾秒循環、氛圍描述給誰去做）。

**4. ID 前綴表沒有「障礙物」和「可拾取道具」— 而全疊範例都在講這兩種東西**
`04 §1` 的七個前綴（BG／CH／VH／TP／FX／EV／UI）是遊戲7 的題材殘留：TP 是「建築零件與建築物」，EV 在 `00 §3` 甚至被定義成「陣頭遊行（舞龍、舞獅）」。但 `01 §2`、`02 §4`、`02 §8` 通篇拿遊戲8 的「要跳過去的地面障礙」「要蹲下躲的空中障礙」「松果道具」當教材，而 `04 §1` 又明令 `OBS` / `ITEM` 是舊制、新遊戲不准沿用。任何跑酷／閃避／收集類的新遊戲，GPT 在編第一個 ID 時就沒有合法前綴可用。

**5. 一款遊戲總共可以做幾張圖，沒有上限**
`00 §3 階段4` 和 `04 §4` 只規範「一批 6～8 張」，從未規範總量。而 `03` 開頭說一款「三、四十張起跳」、遊戲7 做了 45 張分七批、「一天的生圖配額做不完」，`素材工作流/README §6` 更把生圖額度列為「機率最高的失敗點」。GPT 在企劃階段完全沒有成本訊號，每多設計一個動作＝多一張圖＋多一份跨批一致性風險，必然開出做不完的企劃。缺的是 `00 §3 階段1` 的一條硬性限制：這款遊戲的素材預算是 N 張、M 批。

**6. `qa.ps1` 的 fail 級清單沒給 GPT，其中一條它根本不可能知道**
`03` 開頭說「fail 的必須重生（燒生圖額度）」，卻只點名兩條（主體被切到、去背失敗）。實際 `qa.ps1` 有八種 fail：`EMPTY_IMAGE`／`NO_ALPHA`／`EDGE_CLIPPED`／`FRAG_AT_EDGE`／`PALETTE_DRIFT`／`TILE_EDGE_SOFT`／`SHEET_GUTTER_MISSING`／`FRAME_SCALE_DRIFT`。其中 `PALETTE_DRIFT`（qa.ps1:510-514）會檢查素材裡「招牌色」的像素佔比是否達標（目前寫死成松鼠橘 ≥6%、披風藍 ≥1.5%），不達標就 **fail**。沒有任何一份文件要求企劃或場景設計指定「招牌色與其最低佔比」，`04 §3` 的「畫風前綴」欄也不含色票。GPT 無從滿足、也無從自我檢查這條。

## 二、矛盾

**1.（最嚴重）「幾何由 build.ps1 正規化」是假的，而它是全疊禁止寫幾何規格的唯一理由**

- `00 §3 階段3` 的 `組` 欄：「同一組會一起跑幾何正規化」
- `04 §3`：「填同一個組名的圖，本機會一起做一致性處理與量測」
- `00 §4`、`01 §10.8`、`02 §4`、`04 §7.6`：「統一尺度、統一水平中心、統一底線全部由本機 `build.ps1` 正規化解決」
- vs `05 §6`：「`build.ps1` 並沒有讀這個欄位……別讓下一個人以為它自動做了」

查證結果是 `05 §6` 對，而且比它說的更糟：`build.ps1` 全檔沒有「組」「正規化」「baseline」等任何字樣，只讀 `$a.id` 與 `$a.輸出.{knee, 裁切, 水平翻轉, 格式, webp品質, 去背}`，處理步驟就是「三路分流去背 → 邊緣羽化 → 裁切／縮放 → 存檔」。**統一尺度／統一水平中心／統一底線的程式碼不存在。** 諷刺的是 `03 §4` 末段那句對 build.ps1 的描述（去背→依內容裁切→翻轉→縮放→WebP）完全正確，作者其實知道。

而且「依內容邊界裁切再縮到同一寬度」不只沒有正規化，還會**放大**影格落差——`05 §6` 自己量到小師傅四張同寬 400px 之後圖高是 995／679／1020／626。更致命的是 `qa.ps1:643` 的 `FRAME_SCALE_DRIFT` 是 **fail 級**（同組 `area_frac` 最大/最小比超過容差就判退）。也就是：文件叫 GPT 別管的東西，驗收會判退、會燒額度重生。這一條不修，整疊文件的核心論證是空的。

**2. 旁白到底是英文還是中文，三份文件三種答案**

- `00 §1.3`：「**語音一律英文**（磨耳朵）」
- `00 §3 階段1`：「每句**英文旁白**（給 Gemini 產 TTS）＋對應的**中文畫面文字**」
- `01 §8`：「**預設英文**」，遊戲8 的中文預錄是要特別寫明的例外
- `04 §5`：「『旁白台詞』用表格交，三欄：編號｜**中文台詞**｜播放時機」

`04 §5` 是唯一規定交付格式的地方，而它**沒有英文欄位**。GPT 照 04 交就必然違反 00。管道也一樣分裂：`00 §2` 把所有語音路由給 Gemini 產 `mic/sNN.mp3`（那是遊戲8 的中文預錄架構），`01 §8` 卻說遊戲1～7 走瀏覽器 `SpeechSynthesis`。預設語言與預設管道兩件事都沒有單一答案。

**3. prompt 裡到底能不能出現檔名**

- `04 §2` 標題就是「ID 絕對不可以出現在 prompt 裡」，內文明列「不准出現 ID、編號、**檔名**、hex 色碼」
- `05 §4` 模板第一行就是「完全沿用 Sources 裡 **REF001.png** 的那個角色」，並宣告「**檔名是 prompt 裡唯一允許出現的識別碼**」

兩條都是硬規則語氣、都沒有讓步空間。而 `03 §6` 那段要貼進 Project instructions（服從權重最高的位置）的精簡版第 3 條又禁止圖上出現任何文字數字字母——`REF001.png` 正是最容易被畫上去的字串，`05 §4` 自己也承認只能靠人眼確認。

**4. 角色朝向的預設值，在 3D 遊戲上直接互斥**
`03 §1.8` 與 `03 §6 精簡版第 7 條`都寫死「角色一律面向畫面右邊」，而 `03 §6` 那段會被貼進 Project instructions。但 `02 §3` 對 3D 遊戲宣告「**正面平視是硬性要求**」、「3/4 斜角的圖擺進場景會站歪」，`05 §4` 也記載遊戲7 小師傅四張全是「正面朝向鏡頭」。做 3D 遊戲時，最高權重的那份指令帶著錯的預設值，而文件沒給「哪種遊戲用哪個預設」的判準。

**5. 素材清單是 Markdown 還是 JSON，`輸出` 是不寫還是 `{}`**
`00 §3 階段3`：「交出一份逐張列出的清單。**Claude 會把它轉成** `assets.json`」、「`輸出` 那一欄由 Claude 填，**你不用寫**」。
`04 §3`：GPT 直接交 `assets.json`，`04 §7.7` 要求「可以被直接 parse」，`04 §7.5` 要求「所有 `輸出` 都留空 `{}`」。
（實務上 `build.ps1` 用 `$o = $a.輸出` 後逐項判 `$null`，缺 key 與 `{}` 都能跑；但 GPT 讀到兩種指示只會照一種，而 `00` 那版會讓它交出不可 parse 的 Markdown。）

**6. emoji 能不能用**
`01 §5`：「按鈕一律用圖示或 emoji，**不要用文字標籤**」，`01 §7` 舉的例子卻是「🐿️ 再跑一次！」——帶中文字，同時違反 §5 自己那半句。
vs `00 §3 階段3 規則 3`：「會用 emoji 湊數的地方，寧可少幾種也要全部換成同畫風的圖……AI 圖與系統 emoji 混用非常不協調。」
UI 按鈕該用 emoji 還是該進素材清單，沒有答案。

## 三、稀釋

**1.「不要寫幾何規格」講了九次，同一組實測數字出現五次 — 刪掉八處**
出現位置：`00 §3 階段2`、`00 §3 階段3`、`00 §4`（整節）、`01 §10.8`、`01 §12 表格一列`、`02 §4 引言`、`03 §4`（整節）、`04 §3`（兩次）、`04 §7.6`、`05 §6`（整節）。「19.8pp／8.5pp／16.6%」這組數字被抄了五遍。
這是全疊最嚴重的重複，而且已經重複到互相打架（見矛盾 1）。**建議：完整論證只留 `03 §4` 一處，其餘全部縮成一句「幾何規格不寫，理由見 03 §4」。**

**2. `DONE:{ID}` 哨兵字串的禁令出現六處 — 只留一處**
`00 §5`、`01 §2 前言`、`01 §12 表格末列`、`03 §3 表 #8`、`04 §2`、`05 §4`。這是 GPT 從未主動表現過的傾向，卻用六段篇幅去禁止它。**建議只留 `03 §6` 精簡版最後一行。**

**3. 本機腳本的參數與操作細節，GPT 既不填也不能執行 — 整段移回 README**
`04 §3` 逐項解釋 `knee` 起手 60、`純色容差` 26／60、`邊緣淡出`、`w`/`h` 怎麼從世界尺寸換算；`05 §6` 整段的 `AR`／`KID_FRAMES`／`VEH`、世界高度 1.75／1.25／2.15／2.15、`ART_VER` +1；`05 §0` 與 `§3` 的瀏覽器操作實測（Sources 會不會改名、`file_upload` 只收 session 路徑、10MB 上限、`Delete` 不可逆、「上傳步驟（Claude 執行）」）。這些是 Claude 的操作手冊。
`05 §6` 末尾那句「要嘛補進 `build.ps1`，要嘛改掉那句說明，別讓下一個人以為它自動做了」更是寫給人類維護者的 TODO，出現在 GPT 的 Sources 裡只會製造困惑。**建議：`04 §3` 的 `輸出` 只留「一律交 `{}`」一句，`05 §0/§3/§6` 的本機流程整段刪。**

**4. `00` 幾乎整份是 `01`～`04` 的摘要，而且摘要版已經漂掉了**
`00 §1.3` = `01 §1/§8`；`00 §3 階段1` 的四條硬性限制 = `01 §6/§7/§9/§10`；`00 §3 階段3` 的素材三規則 = `03`/`04`；`00 §4` = `03 §4`。`00` 真正獨有的只有三方分工表與四階段順序。
更糟的是，上一節的矛盾有三條（語音語言、素材清單形態、EV／TP 前綴定義）**就是在 `00` 這份摘要裡漂掉的**——重複不只是佔篇幅，它正在製造矛盾。**建議把 `00` 砍成一頁：分工表 ＋ 四階段名稱 ＋ 「細節看哪一份」的指路表。**

**5. `01 §2` 白名單表的「判定依據」欄與 `01 §4` 的所有門檻數字**
0.72／1.05／1.2 倍肩寬、0.80／0.90、0.48／0.72、每秒 3.2 個肩寬、0.85／1.1／0.14／0.5／2.5 秒……GPT 不寫程式，這些數字對企劃的唯一作用是「證明這個訊號可行」，而可行與否光靠訊號名稱就講完了。**建議保留七個訊號名稱與「每種都要有維持時間確認＋遲滯緩衝」一句，門檻數字整欄刪掉。**（唯一該留的是 `01 §4.5` 的「威脅要提早預告」，那是企劃層的設計手段。）

## 四、危險

**1. 沒有規定一款遊戲最多能用幾個訊號 → GPT 會交出四動詞企劃，實玩是連續誤觸**
`01 §2` 給了七個訊號，`01 §4.3` 只說「同時可能成立的姿勢要排優先序」，但**從未規定一款遊戲最多用幾個**。而「雙手高舉」「雙手高舉並張開」「雙手在身前靠攏」三者全靠兩腕距離切分（0.72／1.05／1.2 倍肩寬）——一個照 `01 §1` 所述「全程蹦蹦跳跳、手一直亂揮」的 4 歲，每秒都會穿越這幾個區間。GPT 會非常自然地交出「蹲＝挖、舉手＝倒、平舉＝滑翔、靠攏＝抓」的企劃，逐條對得上白名單、通過 `01 §11` 全部六題自我檢查，實際玩起來是四個動作互相搶。
**建議明令：一款遊戲最多 2～3 個訊號，且必須是 `01 §10.4` 說的互補對。**

**2.「至少要有一個故意觸發的搞笑事件」會和主玩法搶同一個訊號**
`01 §6.3` 把它列成獨立需求，沒說觸發訊號可不可以與操作訊號重疊。遊戲7 能成立的關鍵是：破壞車只在「壓水泥／吊建材／請神像」三個階段可召喚，與同樣用雙手高舉的「倒水泥」**錯開在不同關卡**。`01 §6.2` 只寫了「在這三個階段可以召喚」，沒寫「所以必須靠階段錯開」——這個因果被漏掉了。GPT 會設計出同訊號、同階段的召喚，結果是小孩每倒一次水泥就砸掉一次自己蓋的房子，而且他不會理解為什麼。

**3.「只描述動作，不要限制道具」被寫成方法論，會生出缺了玩法必需物件的素材**
`05 §4` 把遊戲7「模型自己補上鏟子和水泥桶，剛好對上關卡設計」寫成可沿用的做法，並說「留空間給它發揮」。但這與 `03 §3` 失敗模式 #2／#3（模型自己加東西 → 整張報廢重生）方向相反，而且那次是**運氣，不是機制**。照這條寫 prompt，「倒水泥那格有沒有桶子」變成看模型心情——而「缺了玩法必需的道具」不對應 `qa.ps1` 裡任何一條檢查，會一路綠燈通過 contact sheet 接進遊戲，直到在電視上實玩才發現（這正好是 memory 裡「改完要實際玩過」那條教訓的來源）。
**建議改成：玩法必需的物件一律寫死，只有純裝飾才留白給模型。**

**4. 護眼暫停與「持續逼近」型玩法接不回去，而自我檢查問不出來**
`01 §9` 要求玩法能被凍結 5 秒後原地接回，`01 §11 第 6 題`也只問「能不能」。但 `01 §4.5` 同時鼓勵「算出障礙抵達時間、小於 1 秒就降速」的捲軸節奏。一個正在逼近的障礙如果在距離 0.3 秒時被凍結，5 秒後解除時它就貼在臉上，4 歲玩家沒有任何反應時間。文件從未規定**解除暫停時場上的威脅要怎麼處理**（清場？推回起點？給無敵？）。GPT 會在第 6 題誠實答「可以凍結」，然後交出一份實際上接不回去的設計。

**5.「跳」被平鋪在白名單裡，看起來和「身體左右移動」一樣可靠**
`01 §2` 只寫它是髖部上升速度、遊戲8 用了。但這個 repo 最近五筆 commit（v8→v12）**全部在補救它**：「換上優化素材＋修空中障礙撞不到＋障礙更醒目」→「障礙接近警示改為光暈並加強亮度」→「光暈改為全程顯示」→「跳躍更寬鬆（跳高＋滯空久＋碰撞框縮小）」→「時機輔助（整體放慢＋滯空 1 秒＋障礙接近時慢動作）」。也就是遊戲8 上線後改了至少四版，才讓 4 歲玩得動。
文件沒有任何地方標註「跳是全系列最貴、最需要補償的訊號」，GPT 會拿它當核心動詞來設計，交出一款需要再花四版才能玩的遊戲。**建議在 `01 §2` 的「跳」那一列直接註明這段歷史。**

**6. 堆疊零件的限制只寫成「為什麼要正面平視」的理由，沒寫成禁令**
`02 §3` 提到「廟是台基→台階→後牆→……逐件疊上去的，**槽位寫死在程式裡**」「堆疊零件會被強制拉伸成固定幾何尺寸」，但這兩句是夾在「所以要畫正面平視」的論證裡的，沒有獨立成一條禁令。GPT 讀到「程式會把零件逐件疊起來」，會很自然地企劃出「玩家自己選要蓋哪些部件」「每局隨機組合出不同建築」——對 4 歲極有吸引力、對程式是組合爆炸（遊戲7 的十件是固定順序、固定槽位、寫死的）。
**建議在 `02 §3` 明寫：堆疊順序與槽位是寫死的，企劃不得出現玩家自選組裝或隨機組合建築。**
